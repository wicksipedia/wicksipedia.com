How to Compare Git Diffs Across Multiple Commits

Learn how to diff changes across multiple commits in Git and Azure DevOps — practical diffing techniques and examples.

16 August 2020 · by Matt Wicks

gitterminal

A while back one of my colleagues was investigating an issue on a project he had just re-joined. There had been a lot of work done on various facets of the codebase (from memory there were React and Xamarin front ends and a .NET Core API).

The Problem

He wanted to see all the changes from when he last worked on the Xamarin project while he was away. If we unpack and abstract it, he wanted:

  • for a set of commits from start to end
  • for a given path (folder/file)
  • squash the commits and show the changes

The Potential Solutions

  1. Bad choice — go to the File view for the repo in Azure DevOps and see the list of commits. This lists the specific commits that have changed files under the path but not the actual changes, which is what he needed.
  2. Unknown choice — I'm sure there's a nice GUI that could do this with a click-click-done, but he didn't have one already so this wasn't a feasible option.
  3. Good choice — grab the SHA of the last commit he worked on and run a quick git command.

Here's an example for the repo that creates this site:

# squash every change between two commits into one diff, scoped to a path
git diff 741d760 df32e83b -- gatsby-*.js

# general form
git diff <start commitish> <end commitish> -- <folder/file filter>
sh · full colour

The -- is there to separate the commits and the path. A few related forms worth keeping in your back pocket:

commandwhat it shows
git diff A Bevery change between two commits, squashed into one diff
git diff A B -- paththe same, limited to a folder, file, or glob
git diff A B --stata file-level summary instead of the full patch
git log A..B --onelinethe commits in the range, one per line
After he ran this command, he was able to scroll through and see what had changed on the project — which helped him track down the issue, and when it was introduced.

The advantage of the terminal approach was that it can work for both folders and files (even with file globs), it can be re-scoped by changing the commit range, and if you have git installed — you can run the command.

I'd love to know how you go about solving this type of problem, or what tools you use to help with your git workflow. See also: signing your commits with GPG and managing repository settings as code.
